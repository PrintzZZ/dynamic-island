# 灵动岛 · 音乐模块设计

> 新增一个独立的岛内应用「音乐」：紧凑态胶囊显示歌词，展开态为半高面板（歌词 + 控制器 + 封面）。
> 本文档记录**实测数据、参考实现分析、已定稿的设计与待确认项**，是讨论结论的落档。
>
> 状态：**已实现并通过验证。** 本文档是设计依据；实现中的几处偏差见下面的「实现说明」。
>
> **实现说明（与设计的偏差）**
>
> | 项 | 设计 | 实际实现与原因 |
> |---|---|---|
> | helper 脚本位置 | "随应用打包的 `.ps1`" | **运行时写进 `userData`**。打包后 `dist-electron` 在 `app.asar` 里，PowerShell 无法执行 asar 内的文件；写 userData 就绕开了 asar，也不用改 electron-builder 配置 |
> | helper 生命周期 | 未细化 | 额外加了**父进程存活检查**（每 3 秒）。实测应用被强杀时会留下孤儿 helper，而它只在状态变化时才写 stdout，永远发现不了管道已断 |
> | 在线歌词开关 | 建议"首次弹一次说明" | 改成**默认开启 + 设置项里写明"会把歌名与歌手发送到公开歌词库"**。少一个弹窗流程，信息照样给到 |
> | 歌词目录 | 设置里可改路径 | 固定为 `userData/lyrics`，只提供「打开目录」按钮。够用，先不引入目录选择器 |
> | 控制指令通道 | 未细化 | 主进程写命令文件、helper 每轮读取并删除（延迟 ≤300ms）。PS 5.1 里非阻塞读 stdin 要折腾 .NET 异步，不划算 |
>
> **验证结论**（本机实测）：LRC 解析精确到毫秒；三引擎回退链生效（LRCLIB 最快 395ms/42 行，网易云 1298ms/45 行，QQ 兜底 670ms/63 行）；时长匹配消歧有效；缓存命中 0ms；负缓存生效；本地 `.lrc` 优先级最高；歌词条与半高面板、本地时钟推进、暂停冻结、无歌词回退、停止播放退出接管，全部通过。

## 1. 目标与范围

| 项 | 内容 |
|---|---|
| 形态 | **独立的岛内应用**（和「时间」「效率」同级），不是效率模块下的模式 |
| 紧凑态 | 胶囊**加长**，显示歌词（当前句 + 下一句） |
| 展开态 | **半高面板**：2 行歌词 + 播放控制器 + 封面 + 进度 |
| 数据源 | Windows 系统媒体会话（SMTC） |

## 2. 实测结论：Windows SMTC

### 2.1 可用性 —— 零新依赖

宿主环境本身就是 **Windows PowerShell 5.1**，WinRT 可直接调用，**不需要任何原生模块、不需要 node-gyp、不需要 electron-rebuild**。

```
[Windows.Media.Control.GlobalSystemMediaTransportControlsSessionManager,
 Windows.Media.Control, ContentType=WindowsRuntime]
```

### 2.2 能力矩阵（在真实播放状态下实测）

| 能力 | 网易云音乐 `cloudmusic.exe` | Chrome `chrome.exe` |
|---|---|---|
| 歌名 / 歌手 | ✅ `阳光下的星星` / `金海心` | ✅（标题是抖音页面） |
| 播放状态 | ✅ `Playing` / `Paused` 准确 | ✅ |
| **封面** | ✅ `Thumbnail` 可用 | ❌ `null` |
| 播放 / 暂停 | ✅（`pause=True`） | ✅（`play=True`） |
| 上一首 / 下一首 | ✅ | ❌ |
| 停止 | ❌ | ✅ |
| **拖动进度** | ❌ `pos=False` | ✅ `pos=True` |
| **播放进度** | ❌ **永久拿不到** | ✅ `pos=12.00 / dur=20.11` |

> 控制项的布尔值是**随状态翻转**的：正在播放时只有 `pause=True`，暂停时才 `play=True`。

### 2.3 性能实测

| 操作 | 耗时 |
|---|---|
| 常驻 helper 单次查询（预热后） | **平均 1.4ms**，最大 18.4ms（首次） |
| 一次性起进程 + 查询（含进程启动） | **~900–940ms** |

**结论：绝对不能每秒 spawn 一次进程，必须常驻一个 helper 子进程。** 300ms 轮询的 CPU 开销可忽略。

### 2.4 同时存在多条会话

实测同时看到 `chrome.exe` 和 `cloudmusic.exe` 两条会话，且 **Chrome 那条的标题是「发现更多精彩视频 - 抖音搜索」**。

👉 所以**不能简单地取"当前活动会话"**，必须有目标播放器的选择与过滤规则。

## 3. 参考实现分析：NetSpeed-Dynamic

参考项目：<https://github.com/GEORGEWWWU/NetSpeed-Dynamic>
关键文件：`src-tauri/src/music_controller.rs`

### 3.1 正在播什么 —— SMTC（和我们一致）

- 按**包名子串**匹配目标平台：`cloudmusic`/`netease`、`cn.toside.music.desktop`（落雪）、`browserPro`（浏览器通用）、`other`（优先 JustSolo）
- **过滤抖音**（标题或包名命中直接跳过）
- 目标平台由前端设置，存在一个静态变量里

### 3.2 位置补偿（值得学）

```rust
if is_playing {
    diff_ms = now - timeline.LastUpdatedTime
    if diff_ms > 0 && diff_ms < 86400000 { position_ms += diff_ms }
}
```

SMTC 的 `Position` 只在播放器**更新会话时**才刷新，本身不够平滑。加上"距上次更新的时间差"就能把它变成连续可用的位置。

### 3.3 歌词 —— 三引擎顺序搜索，用「时长」做匹配校验

| 顺序 | 引擎 | 接口 |
|---|---|---|
| 1 | QQ音乐 | `c.y.qq.com/soso/fcgi-bin/client_search_cp?w=…&n=5&format=json` |
| 2 | 网易云 | `music.163.com/api/search/get/web`（POST 表单，伪造 `X-Real-IP`） |
| 3 | **LRCLIB** | `lrclib.net/api/get?track_name=…&artist_name=…&duration=…` |
| 取词 | QQ | `c.y.qq.com/lyric/fcgi-bin/fcg_query_lyric_new.fcg?songmid=…&nobase64=1`（需 `Referer: y.qq.com`） |
| 取词 | 网易云 | `music.163.com/api/song/lyric?id=…&lv=-1&kv=-1&tv=-1` |

**匹配规则（关键）**：歌名匹配 **且**（歌手匹配 **或** 时长差 ≤ 3000ms）；有时长时取时长最接近的一条。

**搜索词清洗（关键）**：

- 去掉前缀 `正在播放: ` / `正在播放：` / `Now Playing: ` / `Playing: `
- 歌名形如 `歌名 - 歌手` 时只取 ` - ` 之前
- 歌手是占位值时视为空：`edge` / `chrome` / `potplayer` / `bilibili`，以及 `网易云`/`云音乐`/`qq音乐`/`酷狗`/`spotify`/`music` 等平台名

**结果修正**：拿到 LRC 后解析 `[ti:]` / `[ar:]` 元数据，反过来修正标题与歌手。

### 3.4 封面 —— 4 路并发抢，3 秒超时

`SMTC 本地缩略图（转 base64）` 优先 → `iTunes Search` → `网易云` → `Deezer` → 兜底一个内联 base64 的 SVG 渐变占位图。

### 3.5 一条外接通道（重要）

他们的应用监听 `127.0.0.1:47300`（活动池），并在注释里写明避开了 **`47290`（WS 歌词）**。

`music_controller.rs` 里确实有一个 WebSocket 客户端连 `ws://127.0.0.1:47290/`：

- 连接后先发 `{"type":"hello","client":"NetSpeed Dynamic Pro"}`
- 服务端推送 JSON 或纯文本，原样转发给前端
- 当 SMTC 里发现 `justsolo` 这个包名时，通知前端去连接/重连

👉 **这说明他真正"精确同步"的路径不是 SMTC，而是外接一个歌词源。** 这是对"SMTC 拿不到位置"的正面承认。

## 4. 核心限制与由此决定的同步方案

### 4.1 限制

**网易云音乐永不上报播放进度**：`pos=0`、`dur=0`、`LastUpdatedTime = 1601-01-01 08:00`（"从未设置"的值）。播放中也一样。

**参考实现的补偿逻辑对它无效**：

```
diff_ms = now - 1601-01-01 ≈ 4.25e12 ms
guard: diff_ms < 86400000  → 不成立 → 不做补偿 → pos 恒为 0
```

**结论：在网易云上，逐行同步歌词无法通过 SMTC 实现 —— 参考项目同样做不到。**

### 4.2 方案：A + B

| | 做法 | 适用 |
|---|---|---|
| **A** | **估算同步**：换歌时把本地时钟归零，`Playing` 走、`Paused` 停；若播放器上报进度，则用 `pos + (now − lastUpd)` 做真同步 | 全部播放器 |
| **B** | **手动对轴**：展开态点某一歌词行 = "从现在起按这一句同步"，重设估算基准 | 救回 A 的所有失准场景 |

**A 的失准场景**（必须靠 B 兜）：

- 播到一半才打开灵动岛 → 不知道已经唱到哪
- 用户拖动进度条 → SMTC 看不到，永久错位
- 播放器崩溃/重启

**UI 上的诚实**：未真正同步时不显示精确进度，必要时给一个极轻的提示，不假装很准。

### 4.3 兜底：读播放器窗口标题

**更正一处早先的结论**：一开始根据 Lyricify 官方 FAQ 判定"网易云 Win32 原版根本不注册 SMTC"，**这个说法太绝对**。实测网易云有**一个开关**（默认关闭）控制是否接入系统媒体会话，打开之后 `cloudmusic.exe` 就会正常出现在 SMTC 里。FAQ 那句话针对的是"默认状态"，而不是"做不到"。

但即使开关打开，**网易云仍然从不上报时间轴**：`pos=0 / dur=0`（Lyricify 为此专门提供"使用内置计时器"开关，和我们的 A 方案是同一个思路）。所以：

- 歌名/歌手/播放状态/上一首·播放暂停·下一首：**能拿到**（实测 `canPause/canNext/canPrev = true`、`isCur = true`）；
- 进度：**拿不到**，只能借歌词匹配记录里的时长 + 本地秒表（见 §9.1 与 §12.4 第 7 条）。

而开关关着时（默认状态，也是绝大多数人的状态），会话数是 0，模块什么都看不到。既然不改播放器侧，就在我们这侧兜。

**做法**：helper 每 3 轮（约 0.9s）枚举候选播放器进程的可见顶层窗口，取标题形如 `歌名 - 歌手` 的那一个，随 state 一起上报为 `fb`：

```json
{"kind":"state","sessions":[...],"fb":{"app":"cloudmusic","title":"情非得已","artist":"庾澄庆"}}
```

主进程侧只在 `sessions` 里**一条可用会话都没有**时才把 `fb` 合成一条"伪会话"（`titleOnly: true`）。合成会话刻意把 `dur` 置 0，于是它自动落进已有的 A 方案（本地秒表 + 点歌词对轴），下游 `index.js` / 渲染层一行都不用改。真实会话一出现（比如用户把网易云的开关打开了）就自动让位，不需要重启。

| 拿得到 | 拿不到 |
|---|---|
| 歌名、歌手 → 查歌词、查封面 | 播放状态（**暂停时歌词仍会继续走**） |
| 换歌（标题变了就重置秒表） | 进度、拖动感知 |
| — | 播放/暂停/切歌（指令发不出去） |

因此兜底状态下：**控制按钮整行隐藏**（不摆死按钮），进度条位置换成一句提示（`未接入媒体会话 · 歌名读自窗口标题 · 点歌词行对齐进度`），歌词两行可点击对轴。

> 提示里必须写"点歌词行对齐进度"这句：估算时钟是从**检测到这首歌**开始走的，如果 App 是播到一半才打开，初始位置就是偏的，手动对轴是唯一的纠偏手段 —— 不提示等于这个功能用不了。

约束与取舍：

- **只认原生播放器**（`cloudmusic` / `QQMusic` / `KuGou` / `KwMusic` / `Spotify`），**不含浏览器**：浏览器标题是 `歌名 - YouTube`，歌手位是站点名，拿去做歌词匹配只会更糟。
- 只认 ` - ` 这种形态，所以「桌面歌词」「迷你播放器」「网易云音乐」这些窗口标题天然被排除；隐藏窗口（`class=icon`）也不会被枚举到。
- 真实会话一旦出现就自动让位（`pickSession` 优先返回真实会话），**不需要重启任何东西**。
- Win32 枚举那段 `Add-Type` 编译失败也不影响主路径：`$hasWin=false` 时整段跳过。

### 4.4 按需启动：不打开音乐面板就不常驻 helper

**实测数据**（打包后的 exe，启动 22 秒后）：

| 进程 | workingSet |
|---|---|
| 主进程 | 95.2 MB |
| GPU 进程 | 93.1 MB |
| 渲染进程 | 78.1 MB |
| Utility（网络服务等） | 49.2 MB |
| **SMTC helper（PowerShell）** | **101.7 MB** |
| 合计 | 417.3 MB |

也就是说 helper 一个人占了**四分之一**。拆开看更清楚：

```
裸 powershell -NoProfile 空跑      71.7 MB   ← 纯粹是"用 PowerShell 当宿主"的税
我们的脚本（WinRT + Add-Type + 状态） ~30 MB
```

**所以在用户真正用到音乐之前，没有理由付这笔钱。** 做法：

- `musicArmed`（存 `settings.json`）默认 `false`。为假时**不 spawn helper**，快照是空的。
- 用户**第一次把岛展开到「音乐」面板**时，渲染进程调一次 `music:arm` → 主进程置 `musicArmed = true` → 这才拉起 helper，并**记住**这个事实。
- 之后每次启动直接恢复（不打开面板也有歌词条）。

**代价（必须说清）**：歌词条是**被动显示**的 —— "现在在放什么"本身就是 helper 提供的。所以**从没打开过音乐面板的人，播歌也不会看到歌词条**；而且面板在这之前显示的是「正在连接播放器…」而不是「未在播放」（后者会让人以为坏了）。这是省这 100MB 换来的，写在这里备查。

`musicArmed` 属于「使用记录」而不是偏好：恢复默认设置时和窗口位置一样**保留**，否则正在用音乐的人会突然丢掉歌词条。

实测三种场景：

| 场景 | helper | armed | 歌词条 |
|---|---|---|---|
| 全新用户（没打开过音乐面板） | **0 个进程**（Electron 310MB） | false | 无 |
| 刚展开到音乐面板 | 1 个（109MB） | true | 出现，曲目自动补上 |
| 已用过的用户重启（零交互） | 1 个（110MB，自动恢复） | true | 正常（66 行歌词） |

> 还想再省的话，下一步是把 helper 从 PowerShell 换成**极小的 .NET Framework 控制台 exe**（WinRT 在 .NET 下同样可用，现在走的就是 `System.Runtime.WindowsRuntime`），常驻预计 20-30MB —— 那 72MB 的"宿主税"就没了。

## 5. 架构与数据流

```
┌──────────────────────────────────────────────────────────────┐
│  常驻 PowerShell 5.1 helper（子进程）                          │
│  · 启动时做一次 WinRT 初始化（Add-Type + 反射 + RequestAsync）  │
│  · 之后每 300ms 查询一次 SMTC                                  │
│  · 只在「有变化」时向 stdout 打一行 JSON                       │
│  · 单次查询 ~1.4ms                                            │
└────────────────────────┬─────────────────────────────────────┘
                         │ stdout（逐行 JSON）
                         ▼
┌──────────────────────────────────────────────────────────────┐
│  Electron 主进程                                              │
│  · spawn / 守护 / 重启 helper                                 │
│  · 解析 JSON，转成 nowPlaying 状态                            │
│  · 歌词获取：本地 .lrc → 缓存 → 在线（LRCLIB → 网易云 → QQ）    │
│  · 封面获取：SMTC 缩略图 → 在线兜底                            │
│  · 通过 IPC 广播给渲染进程                                     │
└────────────────────────┬─────────────────────────────────────┘
                         │ IPC
                         ▼
┌──────────────────────────────────────────────────────────────┐
│  渲染进程（灵动岛）                                            │
│  · island.nowPlaying 状态                                     │
│  · 胶囊歌词态（接管胶囊）                                      │
│  · 音乐应用的半高展开态                                        │
└──────────────────────────────────────────────────────────────┘
```

**helper 放哪**：随应用打包的 `.ps1`（与 `netstat` 那次性 spawn 的先例相比，这次是**常驻**）。需要用 `-NoProfile -ExecutionPolicy Bypass` 启动；`.ps1` **文件必须存为带 BOM 的 UTF-8 或纯 ASCII** —— 实测 PowerShell 5.1 会把无 BOM 的 UTF-8 当 GBK 读，中文字符串会导致解析报错。

**为什么不让渲染进程直接查**：SMTC 只能在主进程侧（Node + PowerShell）拿；渲染进程没有这个能力。

## 6. 歌词获取

### 6.1 查找顺序

```
1. 本地覆盖      userData/lyrics/<歌手> - <歌名>.lrc        ← 用户手动放的，最高优先
2. 磁盘缓存      userData/lyrics/cache/<hash>.json          ← 含"未找到"的负缓存
3. 在线引擎      按"当前在放哪个播放器"决定顺序，见下表
```

**顺序按播放器走，不再固定 LRCLIB 优先。** 起因是字形：LRCLIB 对中文歌大量只收得到**繁体**
（实测 `難以忘記 初次見你`、`故事的小黃花`），而播放器自家那家的歌词源给的是**和播放器界面上
一致的简体**。所以让"谁在放就先用谁"：

| 在放的播放器 | 引擎顺序 |
|---|---|
| 网易云 | **网易云** → QQ音乐 → LRCLIB |
| QQ音乐 | **QQ音乐** → 网易云 → LRCLIB |
| 酷狗 / 酷我 | 网易云 → QQ音乐 → LRCLIB |
| 其他（浏览器等） | LRCLIB → 网易云 → QQ音乐 |

非中文播放器（浏览器里放的多是英文/简体）保持 LRCLIB 优先 —— 它公开开放、覆盖最广。

| 引擎 | 性质 | 说明 |
|---|---|---|
| **LRCLIB** | ✅ 公开开放 API，专为同步歌词设计 | 有正式文档，无 ToS 风险，返回 `syncedLyrics`；但中文曲库偏繁体 |
| 网易云 | ⚠️ 非官方接口 | 与播放器界面字形一致（简体），带翻译行 |
| QQ音乐 | ⚠️ 非官方接口 | 需要 `Referer`，简体 |

后两个做成**可单独关闭**的开关；关掉后顺序会自动跳过它（LRCLIB 永远在列表里兜底）。

> **缓存 key 必须带上引擎顺序**。同一个"歌名+歌手+时长"在网易云源下是简体、在 LRCLIB 源下可能
> 是繁体，只按歌名缓存会让换播放器之后拿到另一家的版本（反之亦然）。

### 6.2 匹配与清洗

沿用参考实现的思路：

- 歌名匹配 **且**（歌手匹配 **或** 时长差 ≤ 3000ms）
- 搜索词清洗（前缀 / ` - ` 后缀 / 占位歌手 / 平台名）
- 拿到 LRC 后用 `[ti:]` `[ar:]` 反修正标题歌手

### 6.3 缓存

- 正缓存：找到的 LRC 全文 + **匹配记录的时长**（用来画进度总长），按 `歌名+歌手+时长+引擎顺序` 哈希落盘
- **负缓存**：找不到的歌也要记下来，避免每次播放都重复搜
- 缓存目录：`userData/lyrics/cache/`，版本号 `v:2`（v1 条目没有 `dur`，直接当未命中重取）

### 6.4 工程细节

- **换歌防抖**：连续快进会连发搜索请求，需要 debounce + AbortController 取消上一个
- **超时**：单个引擎 3s 超时（参考实现的做法），总预算 ~6s
- **降级**：全部失败 → 胶囊退回"歌名 · 歌手"
- **隐私**：搜索会把歌名歌手发到第三方。默认开还是首次询问一次 → **待定（见 §12）**

### 8.3 内容降级

| 情况 | 胶囊显示 |
|---|---|

### 8.4 KTV 擦除：进度直接画在歌词里

进度不另开进度条，而是画在当前句上：**已唱到的部分是亮色（`#f5f5f7`），没唱到的部分是灰色（白 42%）**，边界随时间从左往右推进。

实现是**两层同文本叠加 + `clip-path` 揭开**：

```
<span class="lyric-line">                 ← position:relative; width:max-content
  <span class="lyric-base">当前句</span>   ← 灰色底层
  <span class="lyric-fill">当前句</span>   ← 亮色层，absolute inset:0，clip-path 从左往右揭开
</span>
```

亮色层跑一条 `lyric-wipe` 关键帧动画（`clip-path: inset(0 100% 0 0)` → `inset(0 0 0 0)`），时长/延迟由 `lineMotionStyle` 算出来：进入当前句时用**负延迟**让它从"实际已经唱到的位置"接着跑，还没到第一句时用正延迟等到那句开始。这样擦除是由 CSS 动画逐帧驱动的，不受 IPC / 定时器频率影响。

- 「动画」设置为关闭时（`lineStaticStyle`）不走动画，直接用静态进度百分比。
- 胶囊和展开面板**共用同一套**（`lineMotionStyle` / `lineMotionKey` / `lineStaticStyle`），两处表现一致。

**关键细节：百分比基准必须是"文字宽度"。** `clip-path` 的百分比是相对元素自身盒子算的，所以 `.lyric-line` 用 `width:max-content` 紧贴文字 —— 挂在外层盒子上时短句（`男 :`）会在唱完之前就整句点亮（实测外层盒 185px、文字只有 56px）。长句由 `max-width:100%` + 底层的 `text-overflow:ellipsis` 截断，**高亮层要用同样的截断方式**，否则两层文字对不齐、露出半个字。

当前句的占比分母优先用**下一句的起始时间**，没有下一句才退回总时长。

**引子阶段（`showTrackIntro`，换歌后 1.8s）**：第一行显示的是"歌名 · 歌手"而不是歌词，且**不启动擦除**（没有高亮层）。面板和胶囊都是这个行为 —— 先看清在放什么，歌词再出现。

### 12.3 已定位：为什么 SMTC 会报零个会话

实测遇到过：网易云确实在播放（窗口标题一直在变），但 `GlobalSystemMediaTransportControlsSessionManager` 返回 **0 个会话**。当时怀疑的方向 —— manager 过期、broker 卡死、我们自己的代码有问题、甚至"被强杀的探测进程把 broker 弄坏了" —— **全部排除**。做法是一个判别性实验：

**自己注册一条媒体会话，看 broker 认不认。**

```powershell
# 播一个静音 wav；CommandManager.IsEnabled = true 就会注册 SMTC
$p = [Windows.Media.Playback.MediaPlayer]::new()
$p.CommandManager.IsEnabled = $true
$p.Source = [Windows.Media.Core.MediaSource]::CreateFromUri([uri]$wav)
$p.Play()
```

| 场景 | `GetSessions().Count` |
|---|---|
| 基线（只有网易云在放） | 0 |
| 自建会话存活时 | **1** — `APP=powershell.exe STATUS=Playing pos=6.04 dur=30` |
| 杀掉自建会话后 | 0 |

→ **broker 完全正常，`GetSessions()` 也完全正常，是网易云那条会话根本没注册。** 根因见 §4.3：原版网易云不注册 SMTC，要靠插件，而插件注入会因为网易云自动更新而失效。

**遇到时的处理**（按代价从低到高）：

1. **先查播放器自己的设置** —— 网易云有一个"接入系统媒体会话"的开关（**默认关闭**），打开它 `cloudmusic.exe` 就会正常出现。实测这一步就解决了本项目的 0 会话问题；
2. **什么都不做** —— 兜底（§4.3）已经能给出歌名/歌手/歌词，只是没有播放状态与控制；
3. 在播放器里手动暂停再播放一次，有时能让会话重新注册；
4. 彻底退出播放器（含托盘/后台进程）再启动；
5. 只有在确认播放器确实没有自带 SMTC 支持时，才考虑装 InfLink-rs 或 BetterNCM（**只装 InfLink-rs**；和旧版 InfLink 同时装会出别的异常）。

排查手段见附录的 `caps.ps1` / `windows.ps1`：先用最小探测脚本确认系统里到底有没有会话，再去怀疑代码。

> 两个 Windows PowerShell 5.1 的坑，都在这上面栽过：
> 1. `[System.WindowsRuntimeSystemExtensions]` 必须在 `Add-Type -AssemblyName System.Runtime.WindowsRuntime` **之后**才能解析，否则报 `Unable to find type`；
> 2. `.ps1` 文件里的非 ASCII 会被当 GBK 读。helper 脚本因此**整份保持纯 ASCII**（包括注释），中文说明一律留在 `helperScript.js` 的 JS 注释里。

### 12.4 做兜底时挖出来并修掉的坑

这几条都是"看起来代码没问题、实际一直没工作"的类型。按严重程度排：

**1. helper 从来没有读到过任何一条真实会话（最严重）**

`GlobalSystemMediaTransportControlsSession.SourceAppUserModelId` 是**属性**，helper 里写成了 `$s.SourceAppUserModelId()`（当方法调用）→ 抛 `does not contain a method named ...` → 被 try/catch 吞掉 → `app` 恒为空。而 `pickSession` 第一行就是 `filter(s => s && s.app)`，于是**所有真实会话都被当噪音丢掉**，模块永远显示"未在播放"。`isCur` 也因此恒为 false。

修法：加 `Get-AppId`，属性优先、方法形式作为兜底。**判据**：helper 直接 dump 出来的 `STATE` 里 `"app":""`，而同一时刻独立探测脚本（用属性访问）能拿到 `chrome.exe`。

**2. LRCLIB 在"没有时长"时被整个跳过**

`fromLrclib` 开头是 `if (!sec) return null` —— 而兜底路径恒定 `durationMs=0`，于是最可靠的主引擎直接不参与，只剩两个非官方接口。修法：没有时长时改走 `/api/search` 自己挑一条。

**3. 纯文本歌词会中断引擎回退**

`findLyrics` 里只要引擎返回非空 `lrc` 就 `break`，然后才去 `parseLrc`。LRCLIB 有的歌只有 `plainLyrics`（无时间轴），解析出 0 行 → 直接判失败并写负缓存，**网易云/QQ 明明有带时间轴的结果也永远拿不到**（`今天你要嫁给我` 就是这么丢的：0 行 → 修好后网易云 112 行）。修法：只有"解析出带时间轴的行"才算命中，否则继续问下一个引擎。

**4. 多歌手永远匹配不上**

三个源的歌手分隔方式完全不同：LRCLIB 用 `", "`、网易云把多歌手**直接拼在一起**（`Justin BieberLudacris`）、窗口标题用 `/`（`陶喆/蔡依林`）。原来拿整串互相 `includes` 必然失败。修法：按 `[/,;&、·|]` 与 `feat./ft.` 切词后做集合匹配。

**5. 控制指令打到了"系统当前会话"而不是选中的那条**

helper 的 `Invoke-Command` 用 `$mgr.GetCurrentSession()`。用户同时挂着浏览器会话时（实测 Chrome 的抖音页），点"暂停"会暂停浏览器而不是界面上显示的播放器。修法：指令格式改成 `cmd|app`，helper 优先按 app 找那条会话，找不到才退回 `GetCurrentSession()`。验证：发 `pause` 后 powershell 那条变 `Paused`、Chrome 全程 `Playing`。

**6. 展开面板底部漏一条空白带 + 提示与来源标签重叠**

`.music-app` 的父级（`.island-body`）是 `display:block`，所以 `flex:1` 根本不生效，面板一直按内容高度撑开（实测 135px / 宿主 200px）。隐藏控制行后空白更明显。修法：`.music-app` 加 `height:100%`，多出来的空间由 `.lyric` 吸收（103px，两行居中）；同时 `padding-bottom` 从 8px 提到 20px，给右下角 `bottom:6px` 的 `.source`（歌词来源）让位，否则它和最后一行流内容叠在一起。

**7. 进度总长只能借歌词匹配记录的时长**

网易云（开不开 SMTC 都一样）不给时间轴，于是进度条没有分母。三个引擎的搜索结果里本来就带时长（LRCLIB `duration` 秒、网易云 `duration` 毫秒、QQ `interval` 秒），匹配到哪条就用哪条的时长补上。

两处配套：
- **缓存版本升到 v2**。v1 条目没有 `dur` 字段，如果照常命中，升级后会出现"有歌词但永远没进度"，一直拖到缓存自然过期（正缓存 180 天）。判定条件从 `j.v !== 1` 改成 `j.v !== 2`，老条目当未命中重新取一次。
- **界面标注"估算"**。总长来自歌词记录、位置来自本地秒表，两者都不精确，所以时间后面挂一个 `估算` 角标，不假装精确。

**8. KTV 擦除挂错了层级会失真**

擦除用的 `linear-gradient` 百分比是相对**背景盒子**算的。第一版把渐变挂在外层容器上，实测容器 185px、文字只有 56px —— 短句（`男 :`）会在唱到三分之一时就整句变亮。修法：渐变挂到一层 `display:inline-block; max-width:100%` 的内层 span 上，让它紧贴文字宽度；长句仍由 `text-overflow:ellipsis` 截断。验证方式是直接读 `getComputedStyle(el).backgroundImage` 里的断点百分比：把进度人为对齐到当前句正中（`musicRealign`），断点应落在 50% 附近（实测 50.96 / 53.36）。

**9. 引擎顺序固定 LRCLIB 优先 → 中文歌拿到繁体**

LRCLIB 对中文歌大量只有繁体条目（实测 `難忘初次見你`、`故事的小黃花`），而用户在网易云里看到的是简体，两边对不上。改成**按当前播放器决定顺序**（网易云在放就先问网易云），LRCLIB 放最后兜底。验证：同一首 `晴天 / 周杰伦`，`[lrclib,…]` 得到 LRCLIB 的 `故事的小黃花`（繁体），`[netease,qq,lrclib]` 得到简体。

配套：**缓存 key 必须带上引擎顺序**。否则第一家用 LRCLIB 播过之后，第二家用网易云播同一首歌会直接命中繁体缓存。key 从 `歌名|歌手|时长` 变成 `歌名|歌手|时长|引擎顺序`。

**10. 展开面板的布局和动画与胶囊不一致**

三处：
- 面板第一行用的是 `currentLine`，而它在引子阶段**故意返回空**（useMusic 的设计：由 `displayText` 负责显示歌曲信息），于是面板前奏期只显示一个 `…` 占位符。改成用 `displayText`，并复用 `showTrackIntro` / `lineMotionStyle` / `lineMotionKey` / `lineStaticStyle`。
- 歌词块 `justify-content: center`，歌词浮在面板中间、和上面的曲目信息脱节。改成 `flex-start`（实测间距 6px）。
- 面板还在用旧的 `lineWipe` 渐变方案，和胶囊的 clip-path 动画不是一套。统一成 clip-path 之后删掉 `lineWipe`（它只为面板保留，已无引用）。

另外 `nextLine` 在引子阶段返回的是 `list[1]`（第二句），而此时第一行显示的是歌曲信息，等于**跳过第一句**。改成返回 `list[0]`。

## 13. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 非官方接口随时失效 | 歌词拿不到 | LRCLIB 放首位；接口失败静默降级；做成可关 |
| 隐私（歌名歌手发往第三方） | 用户顾虑 | 首次询问 / 可关闭 / 默认只用 LRCLIB |
| 常驻子进程是新增的运维面 | 崩溃、残留、日志刷屏 | 随应用启停；崩溃重启有限次；stderr 静默收集 |
| 匹配错歌（同名不同曲） | 显示错误歌词 | 时长校验（≤3s）；允许用户手动指定 .lrc |
| 估算同步漂移 | 歌词对不上 | 手动对轴（B）；UI 不假装精确 |
| 浏览器会话污染 | 显示无关内容 | 目标播放器选择 + 抖音等关键词过滤 |
| `pos=False` 时拉进度条无意义 | 控制器残缺 | 按 `Controls` 能力禁用对应按钮 |
| 兜底只读得到窗口标题 | 暂停时歌词继续走；App 播到一半才打开时初始位置偏移 | 提示里写明"点歌词行对齐进度"；真实会话一出现立刻让位；控制行整行隐藏 |
| 窗口标题被改（播放器换皮肤/换版本） | 兜底读不到歌名 | 只认 `歌名 - 歌手` 一种形态，读不到就安静退回"未在播放"，不猜 |
| 负缓存 TTL 30 天 | 接口临时抽风会被长期记住 | 删 `userData/lyrics/cache/` 即可；正缓存 180 天 |
| 进度总长借自歌词记录 | 与实际音源可能有几秒出入；匹配错歌时总长也会错 | 时间后标"估算"角标；位置本来也是本地秒表 |

## 15. 附录：其他可优化项

讨论中一并梳理出来的、与音乐模块无关但值得做的优化。

### 15.1 体积与性能（收益明确）

| # | 项 | 现状 | 建议 |
|---|---|---|---|
| 1 | **字体体积** | `MiSans-Regular.woff2` 4.86MB + PingFangSC 五个字重 ~25MB + InterVariable 0.35MB，合计约 **24MB** | **子集化**，只保留界面实际用到的字符，可压到 1MB 以内。这是打包体积里最大的一块 |
| 2 | `.pill` 的 `will-change` | 常驻 `width, height, border-radius, top`，永久占用合成层 | 只在形变期间添加，结束摘掉 |
| 3 | 时间应用心跳 | 模块级 250ms 定时器，岛收起、无计时无提醒时仍每秒重渲染 4 次 | 按"是否有正在跑的东西"降到 1s |
| 4 | 网速应用 | 每秒 spawn 一次 `netstat -e`（单次 ~140ms 进程） | 仅在网速页可见时采样，或换更轻的取数方式 |
| 5 | 剪贴板轮询 | 固定间隔 | 岛隐藏时放缓 |
| 6 | `pulsePill` | `animationend` 监听有叠加泄漏风险 | 加一次性守卫或改用 CSS 动画 |

### 15.2 架构与一致性

| # | 项 | 说明 |
|---|---|---|
| 7 | 卡片几何常量共用 | 时间与效率目前共用 `PEEK = 10`，两者面板宽度需求不同；`expandedW` 的口子已留好 |
| 8 | `useTimeApp` 的 `visibleModes` | 已不再被外部使用，可收成模块私有 |
| 9 | 新增常驻子进程的规范 | 音乐 helper 是本项目第一个常驻子进程，需要统一的生命周期与日志约定 |

### 15.3 音乐功能自身

| # | 项 | 说明 |
|---|---|---|
